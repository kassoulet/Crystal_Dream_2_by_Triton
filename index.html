01 / The demo, running

Not a recreation.
The demo’s own run.

Every picture and every sound below comes out of CD2.EXE. Its own start-up code, its own protected-mode extender, its own timer interrupt and mixer, and all of its scenes run, instruction by instruction, on a small virtual PC I wrote around the Unicorn CPU emulator. The run was recorded (video, palette and CRT timing at every retrace; the sample stream the demo writes to the parallel port) and this player decodes and shows that recording. No effect, model, texture, text or tune is redrawn or remixed in JavaScript. Use the slider to seek, ←/→ to jump 5 seconds, ,/. to step one frame while paused.

4:3 screen. Each frame is placed from the CRT registers the demo programmed for it (line and frame length, blanking, pixel doubling), so windowed effects keep the size and the black borders they had on a monitor. The audio is the demo’s own output to a Mono Lpt DAC at its 44.2 kHz mixing rate.

What runs

  • The unpacked program (tools/img.bin, produced by the EXE’s own unpacker) from its entry point 1000:0151: Borland runtime, unit initialisations, the protected-mode switch, selector and heap management, every scene
  • The demo’s IDT and its timer handler. The mixer runs at 44.2 kHz inside it and writes each sample to port 378h
  • Its own setup menu (I pressed ↓ ↓ Enter for Mono Lpt 1 and ↓ ↓ ↓ Enter for 44000 Hz), the “Attention” card, the intro, cube and spacecut, plasma, fractal zoom, Vectorslime, tunnel flight, the raytraced pictures, Earth with its scroller, the chessboard and the main menu with its pages

What I supplied

  • DOS: the INT 21h calls it uses (files are served from CD2.EXE itself, where its archive lives), conventional memory blocks, an XMS driver with 8 MB, the BIOS tick
  • The VGA (sequencer, CRTC, graphics controller with write modes 0–3, latches and read modes, attribute controller, DAC), the 8254 timer, the 8259 interrupt delivery, the keyboard (scancodes from the key script above) and the printer port
  • Time: one virtual clock counted in timer counts. The CPU is assumed to run 30 million instructions per second; the retrace flag and the display sampling follow the CRT timing the demo programmed

What this does not prove

  • It is one run with one setup choice. Another sound device, mixing rate or CPU speed changes the audio and can change the pace of scenes that adapt to the frame time
  • My VGA and timer models are not a real card: an effect that relies on a corner I did not model would differ. The scenes I could compare against screenshots of the original match them
  • The monitor model has two constants (how much of each line and frame a monitor spends on flyback); they are set so that the standard 320×200 mode fills the screen

02 / The production

A Pascal program with assembly inner loops.

On 30 May 1993 the Swedish group Triton released Crystal Dream II for MS-DOS. It took 1st place in the PC demo competition at The Computer Crossroads 1993 (Demozoo, pouët).

The authors’ own Comments page lists the show in order: a setup screen, an intro with a built-in performance tester, a vector scroller, objects and a “spacecut” (polygon intersection), a plasma, a fractal zoom, vectorslime, a tunnel flight, four raytraced pictures, an Earth made of 264 textured polygons, a chessboard (1,837 coordinates, 1,628 polygons, one moving light) and the endpart. The page below plays them in that order.

The demo says what it is made of: “programmed in Borland Pascal 7.0 (Assembler of coz) and the sourcecode is 43800 lines long (about 1Mb). The demo runs in protected mode. (NOT under a DPMI server.)” The binary agrees: it carries Borland’s runtime, sets up its own descriptor tables, and refuses to start under a V86 memory manager.

03 / The file

A normal-looking EXE
that is mostly not an EXE.

CD2.EXE begins with a perfectly ordinary DOS MZ header. Then it does something unreasonable: the header says the entry point is CS:IP = FFF0:0100. DOS adds the load segment to CS and truncates to 16 bits, so CS becomes load − 0x10 and the linear address (load − 0x10)·16 + 0x100 is exactly load·16: the first byte of the module. It is the same convention as a .COM file (CS = PSP, IP = 0x100), applied to an EXE.

The header also declares an image of 79,273 bytes including the 96-byte header (e_cp = 0x9B, 155 blocks of 512 bytes), so DOS loads a 79,177-byte module and stops. The other 3,075,306 bytes are an overlay: a private archive of 58 files that the program reads from itself at runtime (see section 05). The executable is a small unpacker with a very large suitcase.

A 588-byte decoder is copied to just below the top of conventional memory (5DBB:0000 in my emulation; the segment depends on available memory), where it unpacks a flat image (≈319,744 bytes; last non-zero byte at 0x4E0FF) into memory, patches its relocations, sets up a stack, zeroes every register, and far-returns into the demo. No external decompressor. No DOS extender. No second file.

What is actually in the overlay?

Strings in the unpacked image name the assets: mainm256.tga, Raytrac1.TGA, TRN-L3.TGA, MEGAFRAC.DAT, Texture2.lbm, Earth3.TVO, shd_cube.tvo, nfly2.tvw. The blob is a custom archive of raytraced stills, textures, fonts, 3D objects and four music modules. Section 05 explains its layout.

Why a generic extractor fails

The overlay has no ZIP, LBM or TGA header at its start, and the file data is XOR-scrambled with a position-dependent term. The directory lives at the end of the EXE, not the beginning. The first 6,254 bytes (a word 0x061B and ascending dwords 0x154, 0x159, …) are not part of that scheme and remain unexplained.

04 / The loader

588 bytes that unpack
a 320 KB program.

The stub is a compact LZ-style unpacker. It first moves the packed image upward with a backwards rep movsw, walking 64 KB chunks and adjusting ES/DS between them, then decodes a bitstream where a 0 bit means “literal byte” and a 1 bit starts a match. Lengths and offsets use small variable-length codes backed by lookup tables at CS:020E, 0219, 0224 and 0234.

At the end of the stream it runs a relocation pass: it reads a list of 16-bit offsets, adds the load segment, and writes the result back. Then it loads SS:SP, pushes the entry CS:IP, zeroes AX BX CX DX BP SI DI, and executes a far return. The unpacked program starts with a completely clean register file, as if DOS had loaded it directly.

The only failure path is the string Not enough memory$. Literals are XOR-ed with the bit counter in DL (the xor al,dl below), a cheap scrambling that defeats naive string searches of the packed file. I have not identified the packer; it may well be an off-the-shelf tool rather than Triton’s own code, so I make no claim about who wrote it.

05 / The runtime

It brings its own
protected mode.

The image contains lgdt, lidt and mov cr0,eax (at 0x2F047, 0x2F04C, 0x2F07B, 0x2F147) and a far jump to selector 00B8. So the demo builds its own descriptor tables and flips CR0.PE itself, with no DOS extender in the file. The check for hostile environments is spelled out in its own error text: “This program requires a 80386 or 80486 CPU. The CPU is in Virtual 8086 Mode! Remove any EMM386/QEMM386/386MAX memory manager and quit all multitasking environments such as Windows, Desqview etc.”

Extended memory comes through XMS (INT 2F AX=4300/4310, then far calls through the driver pointer at DS:EC92); another error string is “This program requires HIMEM.SYS”. The VGA is driven directly: 96 mov dx,0x3C4 sites (Mode X plane select), the CRTC at 0x3D4, retrace polls on 0x3DA.

The CPU-type probe and the long-integer helpers that test it are Borland Pascal runtime code, not the demo author’s (see routine 08 below).

06 / The archive

58 files hidden
inside the EXE.

The 3 MB overlay is a private file archive. The demo opens itself and treats the tail of the EXE as a directory. I found it by following the demo’s own open routine (image offset 0x2FAF2), then confirmed it by decoding every file: all four music files parse as MODs, all IFF files have valid chunk sizes, and the TGAs are real pictures.

The layout, all verified:

  • EOF − 4: dword 0x135A9, where the overlay starts.
  • EOF − 6: word, the file count (58), XOR 0x55.
  • Directory: 58 × 21 bytes ending there, XOR 0x55: a length-prefixed 12-character name, a dword offset, a dword size.
  • File i sits at EOF − offset. Files are stored in reverse order and are contiguous.
  • Data: plain[j] = ((raw[j] ^ 0x5A) + 21·⌊j/64⌋) & 0xFF, with j the offset inside the file. That odd rolling term is why a plain XOR gives pictures with horizontal stripes.

MegaFrac.DAT, deplaned (4096 × 128)

Four VGA planes of 1,024 columns interleave into one 4,096 × 128 strip (the last 16 KB of the file is not picture data: the demo reads it into its code segment as the per-column table). The strip is log-scaled: the scene’s column map is round(i/8 + 68.1·ln((j+1)·2²⁴/500)), 47.2 columns per octave, so scrolling it by 944 columns is exactly 20 octaves, the authors’ “zoomfactor of 1048576”. The Fractal scene plays it with the original scaler’s pixel map.

07 / The code

Eleven routines,
and who wrote them.

Every listing below is generated from the unpacked image by tools/gen_asm.py, so the bytes cannot drift. Each card says who probably wrote it: asm-style means 386 code inside a 16-bit Pascal program with no compiler frame, Borland Pascal runtime and compiler output mean the opposite. The demo’s own Information page says “Borland Pascal 7.0 (Assembler of coz)”, i.e. inline asm blocks inside Pascal, so “hand-written” remains an inference from style.

Mode X splits a row across four planes, so a plain left-to-right copy would need a plane switch every pixel. This loop turns the copy sideways: for each of the 320 columns it does one OUT DX,AX to pick the plane, then walks 200 rows with movsb. That is 320 port writes instead of 64,000. The two odd-looking constants are strides with the movsb auto-increment folded in: +0x13F (319) plus the 1 from movsb is a 320-byte source row, and −0x51 (81) plus 1 is the 80-byte Mode X row. The routine appears twice back to back; the second copy writes through ES = 0x30, a flat selector.

08 / The effects

What the screen is doing,
and why it is fast.

The cards above show how single routines work. This part is about the effects they add up to. A 386 of the time ran a few tens of millions of instructions per second, and the VGA could be written one byte at a time over a slow bus. At 70 frames a second that leaves a few hundred thousand cycles to fill 64,000 pixels, so every effect is built around doing less, or letting the VGA do more.

The VGA does the work: planes, latches, masks

Two video layouts are used. The 256-colour modes are unchained (Mode X): the card’s memory is four planes and one CPU write can reach any subset of them, which allows four pixels per store, several pages in 256 KB, and flipping pages by writing the CRTC start address on the beam (see the “Flip on the beam” card). The intro and the cube scene use 16 colours, where each plane is one bit of the colour and each byte holds eight pixels. There the graphics controller is the clever part: with write mode 3 the CPU sends a bit mask, the colour comes from the set/reset register, and the sequencer map mask chooses which planes receive it. A filler writes only a mask byte per eight pixels and never reads video memory.

That also gives glass for free. Planes are independent, so a face drawn with colour 2 into plane 1 only changes bit 1 of what is already there. The translucent crystals and the glowing slab of the cube scene are ordinary opaque polygons written into some planes; where they overlap other faces, the palette entries for the combined bits show a blend. Nothing is read, nothing is mixed per pixel, and the palette entries for the combined indices are what make the result look like glass (I saw the plane masks in the logged calls; the palette design is inferred).

Polygons: two engines

The wireframe intro and the cube use a small 16-colour engine; the tunnel flight, Earth and the chessboard use a 256-colour one. Both draw back to front in painter’s order, with no depth buffer: faces are drawn in the order the engine emits them (I logged this order, I did not reverse how it is chosen), so there is no per-pixel depth test to pay for.

The projection is cheaper than it looks. A vertex becomes x' = ((x + x/4) · F) / (z + z0) + centre, y' = (y · F) / (z + z0) + centre. The x + x/4 is a shift and an add, and it is the 5:4 correction that makes a 320×200 picture look right on a 4:3 monitor; it costs no extra multiply. There is one divide per vertex, each vertex is projected once into a table and every face that uses it reads the result, and faces closer than a near distance are clipped in 3D before projection rather than per pixel afterwards.

Flat faces are filled four bytes at a time: the colour byte is copied into a 32-bit register and each span is stored as 32-bit words with a few bytes at the ends. Textured faces (Earth, the chessboard) take a 256×256 texture and walk it with 8.8 fixed-point texture coordinates, interpolated linearly across the face, with no per-pixel division. Faces are small and curved surfaces are cut into many of them, so the lack of perspective correction is hard to see, and the inner loop is a handful of instructions. Lighting is a table: a texel is passed through a 256-byte shade row picked from the face’s light value (one xlat instruction), so shading costs one lookup per pixel and no arithmetic on colours.

The scanline routines themselves are generated and patched at start-up, into the demo’s own code segment (the “Patch the loop, not the index” card shows the idea). The step sizes of the current face are written into the instructions as immediates, so the inner loop needs no registers for them and nothing is loaded in the loop.

Tunnel flight, Earth and the chessboard

The tunnel is a world file, a chain of segments rendered with the same polygon filler as everything else; the black bars above and below are the demo’s clip window, which the filler checks per face, so nothing outside is ever drawn. The Earth is a sphere of 264 faces with one map texture and a flat light, and the perspective text scroller over the chessboard goes through the same textured-face path. The chessboard is the original board and piece models with a marble texture and one moving light, drawn into a RAM buffer and copied to the screen in one block, which keeps the partial drawing of a frame off the screen.

Effects that avoid 3D

Plasma. Every pixel is a sum of three sine-table lookups, T[p1+2y+7x] + T[p3−3y] + T[p4−y], written as 4-pixel blocks and two identical lines per store, which is a quarter of the pixels and half of the rows. The offsets are patched into the loop’s own instructions at the top of each frame. The palette routine runs per frame too; I have not worked out how much of the motion it carries.

Fractal zoom. The picture is not computed live. It is a log-mapped strip (MegaFrac.DAT) in which zooming in is just scrolling, and each screen column is a vertical slice of the strip scaled by a per-column factor. The scaler is a branch-free Bresenham in one register (the “Scale a column with an end-around carry” card), so a zoom that looks like a rendered Mandelbrot costs one pass over 320 columns.

Vectorslime. The object is rendered small, into a 120×100 buffer, and each screen is assembled from 40 earlier buffers picked by sine tables, so the object leaves trails and echoes. The authors’ own comment says it: the drawing of the current frame uses previously drawn frames. One small 3D render per frame, reused many times, gives a screen full of motion for the cost of a handful of blits.

Raytraced pictures. Pre-rendered 320×400 images shown on a 4:3 screen, which is why they look soft and tall; the demo only has to decode and display them, and it fades them with the palette.

Palette, retrace and sound

Fades are done by rewriting the 256 DAC entries, not by redrawing pixels: a fade costs 768 port writes instead of 64,000 pixel writes (a typical use of the DAC; the demo’s fades are the ones in its recorded run). Page flips and palette changes are timed to the vertical retrace, so nothing tears. The soundtrack is mixed in the timer interrupt itself: the 8254 is programmed to fire at about 44.2 kHz (a reload of 27), and each interrupt computes one sample and writes it to the parallel port at 378h, where a simple DAC on the port (the setup menu calls it Mono Lpt) turns it into sound. The interrupt is the sample clock, so no sound card is needed, and the main program only has to be interruptible.

Why it holds together

None of this is one big trick. Each effect picks the cheapest representation: a strip instead of a fractal, a few small buffers instead of a rendered tunnel of light, planes instead of per-pixel blending, a lookup table instead of a lighting calculation, fixed-point instead of floating point, patched loops instead of registers. What remains per pixel is a store, and often not even that. That is how an effect that looks like several hundred thousand operations a frame gets through on a machine that has barely more than that to spend.

10 / Field notes

How this was taken apart.

A

Read the header by hand

Python unpacked the MZ fields. The wrap trick and the 79,177-byte module size came out of the numbers, not a tool.

B

Emulate the unpacker

Unicorn runs the real-mode stub (tools/unpack.py), stops at the final retf and dumps the unpacked image to tools/img.bin. Reproducible with pip install unicorn.

C

Disassemble the dump

ndisasm -b16 on the image, then byte-pattern scans: mov dx,0x3C4 (96 hits), rep stosd (19), shrd (8), lgdt/mov cr0. Dense 32-bit regions were read by hand; the Borland copyright string located the runtime.

D

Frames from the original

The stills in assets/ were captured earlier from the running original under DOSBox. I could not re-run it in this verification pass, so treat them as unaudited.

E

Follow the demo’s own file opener

The Pascal Assign/Reset of an overlay file led (image 0x2FAF2) to the routine that opens the EXE itself, seeks to EOF − 6, reads a count and a 21-byte-per-entry directory. XOR keys 0x55 (directory) and 0x5A + a 64-byte ramp (data) were found by brute force and confirmed by every file’s own signature.

F

Reverse the text blitter

The menu code (image 0x1230–0x13E0) walks 4-byte records and calls 0xFB4, an unrolled 1-bit blitter with a per-pixel rotate. Re-implementing it in Python and labelling the font cells gave back the text of all six pages.

G

Check counts against the authors

The Comments page gives vertex and polygon counts (King 201/183, Pawn 141/120, Knight 108/95, Queen 189/169). The .TVO section sizes reproduce them, which is how the object format was validated.

H

Run the demo’s own scaler

The fractal routine reads a table that the demo loads from the last 16 KB of MegaFrac.DAT. With that table, the eight 64 KB tiles and a log column map as inputs, tools/run_fractal.py executes the unmodified routine under Unicorn; extract_fractal_map.py then records each output pixel’s source and checks its closed form against the emulator (0 mismatches).

I

Run the plasma

Three small routines (table builder, 0x3A82 frame, 0x3A10 palette) run under Unicorn in tools/run_plasma.py; the Python and JavaScript ports are compared with them (table: 0 of 1,024 entries differ, frames and palettes: 0 mismatches), and the browser canvas is checked pixel by pixel against the Python port.

J

Record whole scenes

Where a scene was too tangled to port (the 3D engine with its self-generated scanline code, the VGA latch tricks of the intro), I ran the scene procedure itself under Unicorn instead. The harness fakes only what the demo gets from its surroundings: a heap (GetMem/FreeMem), DOS file calls answered from CD2.EXE so the demo’s own archive reader loads its objects, the retrace and music counters, a small VGA model (write modes 0–3, latches, colour compare, a DAC) and the palette upload. Each retrace or page flip records the screen and the palette. Four scenes were done this way (tools/run_cube.py, run_intro.py, run_slime.py, run_tunnel.py). Getting there meant finding what the real start-up leaves behind: the unit initialisation chain at 1000:0151, the video selector 30h hard-coded in many places, and the stack segment doubling as a data segment.
